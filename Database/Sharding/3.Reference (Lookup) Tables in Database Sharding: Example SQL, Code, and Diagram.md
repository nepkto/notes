# Reference (Lookup) Tables in Database Sharding: Example SQL, Code, and Diagram

---

## 1. Reference Table in a Sharded Environment

We have:
- **Sharded Tables**: `Users`, `Orders`, `Addresses` (sharded by `user_id`)
- **Reference Table**: `Products` (`product_id, name, price, category_id`), **not sharded**

---

## 2. A. Replicated Reference Table: SQL Example

You create the `Products` table on **every shard**:

```sql
-- On every shard (shard_0, shard_1, ...)

CREATE TABLE Products (
  product_id BIGINT PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  price DECIMAL(10,2),
  category_id INT
);

-- Insert data on every shard
INSERT INTO Products (product_id, name, price, category_id) VALUES
  (1001, 'Laptop', 1499.99, 5),
  (1002, 'Smartphone', 699.99, 5),
  (1003, 'Headphones', 199.99, 8);
```

### **Join Example Using Replicated Table (on a shard)**

```sql
-- Get all orders for a user, including product detail, on a single shard:
SELECT o.order_id, o.user_id, o.product_id, p.name AS product_name, p.price
FROM Orders o
JOIN Products p ON o.product_id = p.product_id
WHERE o.user_id = 12345;
```

---

## 2. B. Central Reference Database: SQL Example

One dedicated reference database, used by **all shards**:

```sql
-- Central products_db (not sharded)
CREATE TABLE Products (
  product_id BIGINT PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  price DECIMAL(10,2),
  category_id INT
);

-- Insert products centrally (once)
INSERT INTO Products (product_id, name, price, category_id) VALUES
  (1001, 'Laptop', 1499.99, 5),
  (1002, 'Smartphone', 699.99, 5),
  (1003, 'Headphones', 199.99, 8);
```

### **Application Logic for Central Reference Table:**  
Fetch order from the shard, then lookup product info from central reference db.

#### **Pseudo-Python Code Example**

```python
def get_order_with_product(user_id, order_id):
    # Step 1: Get the correct shard for the user
    shard_num = user_id % 2
    conn = get_shard_connection(shard_num)

    # Step 2: Fetch order info from the shard
    order = conn.execute(
        "SELECT order_id, product_id FROM Orders WHERE user_id = %s AND order_id = %s",
        (user_id, order_id)
    ).fetchone()

    # Step 3: Fetch product info from reference db
    ref_conn = get_reference_db_connection()
    product = ref_conn.execute(
        "SELECT name, price FROM Products WHERE product_id = %s",
        (order['product_id'],)
    ).fetchone()

    # Step 4: Return merged result
    return {
        'order_id': order['order_id'],
        'product_name': product['name'],
        'product_price': product['price']
    }
```

## 3. Diagram of Both Architectures

### **A. Replicated Reference Table on Every Shard**

```
+------------------+   +------------------+
|     Shard 0      |   |     Shard 1      |     ... more shards
|------------------|   |------------------|
| Users            |   | Users            |
| Orders           |   | Orders           |
| Addresses        |   | Addresses        |
| Products (rep)   |   | Products (rep)   |  <-- Reference table is copied
+------------------+   +------------------+
```

**- Joins with Products are local and fast.**  
**- Must ensure each Products table is kept in sync.**

---

### **B. Central Reference Table (Separate DB)**

```
             +-----------------------------+
             |     Central Products DB     |
             |-----------------------------|
             | Products                    |
             +-----------------------------+
                ^          ^          ^
                |          |          |
      +---------+--+ +-----+-----+ +--+----------+
      |  Shard 0   | | Shard 1  | |  ...        |
      | Users      | | Users    | |             |
      | Orders     | | Orders   | |             |
      | Addresses  | | Addresses| |             |
      +------------+ +----------+ +-------------+
```

**- All shards (and application servers) make reference queries here.**  
**- Only one place to update and maintain reference data.**

---

## 4. When to Use Which

| Approach   | Use When ...                                                        |
|------------|---------------------------------------------------------------------|
| Replicated | Reference data is mostly static, joins are needed in many queries.  |
| Central    | Consistency is crucial, reference data changes more often, or very large tables. |

---

## 5. Summary

- **Reference/lookup tables** (like Products) are typically not sharded.
- Options are:
  - Replica on every shard for fast local access.
  - Keep in a dedicated, unsharded database for consistency and simplicity.
- Your application's needs, data size, and access patterns determine the best choice.
